# Translation-unit map of the game code (0x800068A0..0x8028BCD4)

Generated by `python3 -I tools/build/tu_analyze.py` (needs `ninja` to have run once, for
`build/RFEE01/asm`). Machine-readable table: `docs/tu_map.tsv` (one row per TU candidate).
The minimal linkable pieces ("units") are written to `build/tmp/buildtree/tu_units.json`, and
the per-unit build status to `docs/tu_units.tsv` (from `tools/build/try_units.py --asm`: status
`ok` = all C, `ok+asm` = links with the listed functions as asm, see docs/BUILD.md 2b) and the
library sources to `docs/tu_libs.tsv`. A merged `file-closure` row that places is also evidence
that its pieces belong to one TU.

194 is a **lower bound** on the number of game TUs: it is the smallest set of boundaries that
explains every duplicated literal, string and source-file name plus the 39 `__sinit`s. The real
count is higher (most game TUs have no duplicated constant that separates them from their
neighbour), so a "low" TU may hold several original files. What is firm is the unit level:
under the model below no original TU boundary lies inside a unit, and every unit can be compiled
and linked on its own (see `docs/BUILD.md` and docs/tu_units.tsv for which ones pass).

## Model

The game was linked from objects in one link order; each object contributes one contiguous range
to every section, in the same order in every section. Data that only its own TU references pins TU
membership ("witnesses"):

- `.sdata2` literals (float/double/aggregate templates, not strings): MWCC emits them per TU;
- switch jump tables (`jumptable_*` in `.data`, at their function's position in the TU's `.data`);
- `.data` string literals whose users span less than 128 KB (longer spans are global `char[]`);
- `.rodata` string pools referenced from code (e.g. `"GActor.c\0..."`, the assert pools);
- optional (`tu_analyze.py --map-statics`, off by default): labels a per-function symbol map
  (`<file>.symbols.json`) names as a file-local static (`...bss.0`, `sa$42`, guards), when their
  users span less than 128 KB. E.g. lbl_803CB7B8, the static of fn_8006BDCC's file, is also used
  by fn_8006C19C, so no cut can lie between them; it removes 34 cuts, but the larger units it
  makes around 0x802383F4 stop placing, so the default build does not use it yet;
- owners are the functions that reference the item, directly or through a `.data`/`.rodata` table
  referenced from at most four places, never through `.sdata` pointers (`const char* SID_x`
  globals, which made all of `.rodata` look shared).

For every possible cut (before function *c*) the tool computes the number of witnesses that would
straddle it plus, per section, the minimum number of witnesses out of order for the best data cut
(segment-tree sweep, all cuts in ~3 s). Cost 0 = "clean cut". A cut is also rejected when its
`.sdata2` cut is not 8-aligned and the unit after it holds a double (MWCC aligns `.sdata2` of
such an object to 8): 50 cuts dropped. Units = runs between clean cuts.

## Boundary evidence

| evidence | meaning | TU starts with it |
|---|---|---:|
| `sinit` | first clean cut directly after a `__sinit` (.ctors entry). MWCC emits `__sinit` after the TU's own functions | 30 |
| `sinit+tail` | as above, but weak functions (inline/template copies, e.g. the 8-byte getters after `fn_800CF890`) follow the `__sinit`; the cut is somewhere in the tail | 5 |
| `dup1` | a literal value or string occurs twice and exactly one clean cut lies between the copies (MWCC pools identical literals per TU) | 23 |
| `inferred` | a duplicate-pair (or two different `__FILE__` names) forces a cut somewhere in a window of clean cuts; the latest one is used and the window size is given | 135 |
| `range` | start / end of the game code | 1 |

Cross-checks:
- The dtk auto-split objects (`auto_03_*`) only split at `.ctors` entries; the regions
  `rA`..`rT` of `src/game` are exactly those pieces. All 39 sinit cuts are found as clean cuts
  (cost 0 for 31 of them with the final witness set; the rest have one to four mis-classified
  global witnesses), which validates the witness classes.
- Source-file names in assert pools agree with the map: GActor.c, GAnim.c, GCamera.c,
  GMaterial.c, GParticle.c, GShape.c, Prim2D.c, video.cpp, DEMOInit.c each fall into a different TU, and
  the GCamera.c TU (0x8000F48C..0x80011E28) is exactly `src/game/rA_800068A0/fn_8000F48C.cpp`
  (49 functions), as the region-A NOTES say.
- Inlining: MWCC inlines functions defined earlier in the same file (`-inline auto`); a unit cut
  between such functions shows up as a codegen difference when the unit is compiled alone
  (`try_units.py` then retries the run of units that keeps each source file whole).

## Columns of docs/tu_map.tsv

`tu`, `text_start`/`text_end` (end exclusive), `functions`, `units` (clean-cut pieces inside),
one column per data section with the witness-based range (start of the first witness to the start
of the next TU's first witness; only sections with witnesses are filled, non-witness data such as
`.bss` statics and globals is not assigned, and the exact range of a linked unit always comes from
`tools/build/place.py`), `start_evidence`/`end_evidence` (with the window size when not exact),
`confidence`, `source_names` (`__FILE__` strings used inside), `sinit` (the TU's `__sinit`), `region`.

## Known limits

- Global data with a short span can still be taken for a witness (a few sinit cuts cost 1-4).
- Functions without any witness (most small methods) can sit on either side of a boundary; the
  map puts them with the following TU (latest clean cut). `inferred(window n)` marks this.
- `.bss`/`.sbss`/`.sdata` statics are not used: they cannot be told apart from globals by name
  (dtk calls everything `lbl_`), only by their users.
