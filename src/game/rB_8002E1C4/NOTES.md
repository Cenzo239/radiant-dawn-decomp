## Compiler quirks found

- **Destructor null-check chains.** A run of `beq` instructions with no new
  compare comes from inlined C++ base destructors, each with its own
  `if (this)`. In C this matches when written as nested `static inline`
  functions `dN(p) { if (p) dN+1(p); }`. Pass struct member addresses
  (`&p->u[2]`), not `(u8*)p + off`, so the compiler keeps `base+offset`
  addressing.
- **`#pragma use_lmw_stmw on`** works per function (with `reset` after).
  This region mixes `stmw` and `_savegpr`. 80030B58 needs stmw, while
  800310E4, 80032198 and 80032334 use `_savegpr`.
- **Store-to-load forwarding:** `p->s8field = intParam; if (p->s8field < 0)`
  gives `clrlwi` followed by `extsb` (8002EF48).
- **Argument types:** a `clrlwi` on an argument after a ternary means the
  parameter is `u8` while the ternary's value is wider (8002FB78). A
  `clrlwi` after a call means the callee returns `int`.
- **Arguments are evaluated right to left.** The call order inside an
  argument list is reversed.
- **Clamp patterns:** `if (min > x || max < x) return;` gives the
  `bge ok; b end` shape. Operand order matters.
- **Integer 64-bit flags at unit+0x108/0x10C.** `x &= ~2ULL` gives the odd
  `li r0,-1; and` on the high word (80032334).
- **C vs C++ mode.** The C++ front end CSEs the base address of a small
  sdata struct copy (`GXColor c = lbl;`), where C uses four
  `lbz ...@sda21`. Virtual calls need real C++ classes: a C function
  pointer loads the vtable into r7, a C++ virtual call uses r12. When a call
  goes through a known global object, cast to a pointer to stop
  devirtualisation: `((VObj*)&lbl)->draw(...)`.
- **A local struct that holds an address-taken member** keeps all its
  fields in memory. In 80032A34, `{TexObj tex; u16 w, h;}` stays on the
  stack.
- **sdata size:** a `.bss` object declared with a small size (8 bytes) is
  addressed as sdata. Declare its real size (lbl_803CA870 is 0x130 bytes).
- **An uninitialized local** in a chain of else-ifs keeps the parameter
  register (80031C38).
- **Local register order is not simply declaration order** when inline
  temporaries are involved. The 800314CC family is still unsolved.
- **Lazy static with an inlined derived constructor.** A guard byte plus
  `lis r3, vt; li r4, obj; stw r3, 4(r4)` needs two stores: base vtable (dead)
  and then the real one. The dead store changes the register choice and leaves no
  relocation, so the base vtable name can be a dummy extern (`lbl_StateBaseVt`).
  A single store gives desc in r4 and obj in r3, which is what 8003FBC0 wants.
  The order of the guard and object stores varies by function.
- **Calling a vtable that is an `extern lbl_`.** Keep the checker verifying the
  vtable: store it by hand in a plain struct and call through a cast,
  `((Functor*)&f)->visit(...)`. A real C++ object gives `__vt__` symbols, which
  the checker cannot verify.
- **Two loads in reverse order** before a store usually mean an inline with those
  values as arguments (arguments evaluate right to left). See 800403C4, 80041894
  and `visit4(f, u->y, u->x)` in 8003AA60.
- **s8 copied to an s8 local stays unextended.** `s8 x = p->s8field` gives a bare
  `lbz` with `extsb` at each use. A u8 field extends at the assignment.
- **The scan loop (8003A3BC family):** the limit parameter must be `int` with a separate
  `s8` local declared first in the inline. That gives limit r26 and row counter r28.
- **Help windows:** `lbz r30; extsb r30; bl` before a varargs call is an `int` temporary
  (`int v = p->x114;`), not a direct argument. See WIN_HP.
- **Frame size and locals:** a buffer's real size can be read from the distance to
  the float conversion temps above it (800401B0 is 0x60, not 0x68).
- **Global base colouring:** a saved-register rotation around a `lis` of `lbl_803EC898` or
  `lbl_803C8E80` can depend on `((T*)&lbl)->f` versus `lbl.f`, for the whole function: one direct
  `lbl.f` anywhere changes it.
